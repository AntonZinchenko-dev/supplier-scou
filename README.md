# Скаут поставщиков

Прототип сервиса для закупщика кафе, магазина или производства: человек пишет запрос обычными словами («молочка для кафе, Екатеринбург, от 50 кг в неделю»), а сервис собирает поставщиков, проверяет юрлицо и документы, показывает цены и условия и ранжирует всех по понятной оценке. У каждой цифры есть источник: кликаешь — видишь страницу, с которой она взята, и нужная фраза на ней подсвечена.

Это тестовое задание (часть 2) для Goulash.Tech. **Сервис работает целиком в браузере на демо-данных**: сервера нет, поставщики вымышленные. При этом весь путь пользователя рабочий — от запроса до письма поставщику и шорт-листа с выгрузкой в Excel.

## Что можно сделать в демо

- **Написать запрос как есть.** Под строкой поиска сразу видно, как сервис его понял: категория, товары, город, объём, нужные документы. Каждый пункт можно поправить до запуска. Непонятые слова показываются честно, а не молча выбрасываются.
- **Посмотреть, как идёт поиск.** Шаги (разбор → поиск кандидатов → проверка юрлиц → сбор с сайтов → документы → оценка) идут потоком, поставщики появляются в таблице по мере готовности.
- **Сравнить в таблице.** Сортировка по оценке, цене, минимальному заказу и документам. Если в запросе только категория («молочка»), цены сравниваются по самому частому товару, и это подписано в заголовке колонки — молоко за литр не сортируется вместе с маслом за килограмм.
- **Понять оценку.** Полоса из 6 отрезков: товар, доставка, юрлицо, документы, условия, свежесть данных. Под каждым — объяснение в одну строку и ссылка на источник. Важность критериев меняется ползунками.
- **Увидеть риски.** Красные флаги («компания в ликвидации», «все декларации истекли», «на сайте нет ИНН») и жёлтые («возит не каждый день», «нет ветдокументов, а в запросе они нужны»).
- **Открыть источник.** Снимок страницы сайта или выписки из реестра с подсвеченной цитатой.
- **Сравнить 2–4 поставщиков рядом.** Лучшее значение в каждой строке подсвечено.
- **Написать запрос КП.** Черновик письма собирается из того, чего не хватает в карточке: если цены нет — спросит цену, если нет декларации — попросит её.
- **Вести шорт-лист.** Статусы (новый → написали → ждём ответ → КП получено → договор / отказ), дата следующего шага, заметки, выгрузка в CSV, которая открывается в Excel без «кракозябр».
- **Добавить своего поставщика** — того, кого знаете сами. Он попадёт в поиск наравне с остальными.

Пять готовых сценариев на главной показывают разные случаи: молочка, рыба с ветдокументами, упаковка, овощи с ежедневной доставкой, готовая еда.

## Запуск

Нужен Node.js 20.19 или новее.

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # сборка в dist/
npm run preview    # собранная версия на http://localhost:4173
npm test           # модульные тесты: разбор запроса, оценка, письмо, демо-каталог, поток SSE
npm run typecheck
npm run e2e        # сквозная проверка в Chromium на 390, 1280 и 1440 px (нужна сборка)
npm run check      # всё по очереди
```

Для `e2e` нужен Chromium для Playwright: `npx playwright install chromium` (или путь к своему в переменной `PW_CHROMIUM`).

## Как устроено

```
src/
  app/        точка входа, маршруты, стили (токены, база, компоненты, страницы)
  pages/      главная, результаты, карточка, сравнение, шорт-лист
  widgets/    шапка и плашка демо, строка и предпросмотр поставщика, прогресс, просмотр источника
  features/   сравнение, письмо, добавление поставщика, веса оценки, разбор запроса
  entities/   полоса оценки, строка факта со ссылкой на источник
  shared/     контракт API (types.ts), клиент, хуки TanStack Query, справочники, форматирование, UI-кит
  mocks/      «сервер» в браузере: MSW-обработчики, демо-каталог, разбор, оценка, письмо, хранилище
contracts/openapi.yaml   тот же контракт для будущего сервера
tests/                   модульные тесты (node:test через tsx)
e2e/smoke.mjs            сквозная проверка на Playwright
```

**Стек:** React 19, TypeScript, TanStack Query, React Router (хеш-маршруты — нужны для GitHub Pages), MSW 2, esbuild. Ничего лишнего: нет UI-фреймворка и CSS-библиотеки, вёрстка своя.

### Моки по контракту, а не заглушки в компонентах

Интерфейс ходит в API обычным `fetch` по путям `./api/...`. В демо эти запросы перехватывает Mock Service Worker и отвечает из `src/mocks/handlers.ts`; прогресс поиска приходит настоящим потоком Server-Sent Events. Контракт описан дважды и одинаково: в `src/shared/api/types.ts` и `contracts/openapi.yaml`.

Поэтому переход на настоящий сервер — это реализовать те же эндпоинты и выключить MSW. Компоненты, хуки и состояние не меняются.

Состояние демо (история поисков, шорт-лист, свои поставщики, настройки) хранится в `localStorage` браузера и сбрасывается кнопкой «Сбросить демо».

### Демо-данные и правила честности

`src/mocks/data/` — 78 вымышленных поставщиков из пяти городов Урала и Москвы и 384 страницы-источника к ним. Генератор детерминированный (зерно — slug поставщика), поэтому у всех одинаковые данные и тесты стабильны.

Каждое значение в карточке — это `Fact`: само значение, статус («подтверждено» / «не нашли»), дословная цитата и id страницы-источника. Тест проверяет, что **каждая цитата действительно есть на своей странице**. Если факта нет, карточка пишет «не нашли», а не придумывает.

Чтобы демо нельзя было принять за реальные данные:
- ИНН и ОГРН — с заведомо неверной контрольной суммой (тест это проверяет);
- сайты — на домене `.example`, телефоны — несуществующего формата;
- номера деклараций содержат «ДЕМО»;
- на каждой странице видна плашка «Демо-данные».

Среди поставщиков специально есть проблемные: в ликвидации, зарегистрированный месяц назад, с ОКВЭД не по профилю, с истёкшими декларациями, без ИНН на сайте, с недоступным реестром, возящий только транспортными компаниями. На них видно, как работают флаги.

### Оценка считается кодом, а не моделью

`src/mocks/logic/score.ts`. Каждый критерий даёт долю от 0 до 1, итог — сумма «доля × вес», веса в сумме 100. Одни и те же данные всегда дают одну и ту же оценку, и любой балл можно объяснить по пунктам.

| Критерий | Вес по умолчанию | Что учитывает |
|---|---|---|
| Товар | 30 | есть ли нужные товары; «похожий из той же категории» — только 20% |
| Доставка | 20 | возит ли в ваш город, как часто (ежедневно → раз в неделю), холодовая цепь |
| Юрлицо | 20 | статус в реестре, возраст компании, ОКВЭД |
| Документы | 15 | действующие декларации и ветдокументы на нужную продукцию |
| Условия | 10 | минимальный заказ относительно вашего объёма, отсрочка |
| Свежесть | 5 | как давно собраны данные |

Для рыбы, мяса и упаковки веса свои: у рыбы и мяса документы весят 20 вместо 15, у упаковки — 8, зато больше весят доставка и условия. Красный флаг «в ликвидации» блокирует поставщика: оценка не выше 10, строка уходит в конец таблицы.

## Чем прототип отличается от боевой версии

| | Прототип | Боевая версия |
|---|---|---|
| Поставщики | 78 вымышленных | поиск по открытым источникам и картам, свой каталог растёт с каждым запросом |
| Юрлицо | сгенерировано | ЕГРЮЛ через API (DaData / ФНС), проверка ИНН по сайту |
| Документы | сгенерированы | реестры деклараций и сертификатов ФСА, ФГИС «Меркурий» |
| Цены и условия | сгенерированы | извлечение с сайтов и прайсов (в т.ч. PDF и Excel) с проверкой цитат |
| Разбор запроса | словарь и правила | правила + LLM для сложных формулировок, с подтверждением человеком |
| Хранение | localStorage | PostgreSQL, учётные записи, общая история команды |
| Письма | черновик для копирования | отправка с почты пользователя, разбор ответов |

## План развития до боевого сервиса

Каждый этап заканчивается работающим продуктом, который можно показать пользователям. Порядок и объём зависят от ответов на вопросы ниже — например, если сервис только для своих закупщиков, этапы 5–6 сокращаются, а если для внешних клиентов — добавляются оплата и роли.

### Этап 0. Прототип — сделано

Весь путь пользователя на демо-данных, контракт API, тесты. Цель — согласовать с заказчиком и закупщиками, *что* сервис делает, до того как тратить время на источники данных.

### Этап 1. Сервер и реальная проверка юрлиц · ~2–3 недели

- Сервер на FastAPI по `contracts/openapi.yaml`, PostgreSQL, фоновые задачи (очередь на Redis или `arq`).
- Типы фронтенда генерируются из OpenAPI; MSW остаётся для разработки и тестов.
- Вход по почте, данные привязаны к пользователю и компании.
- Проверка юрлица по ИНН: DaData или API ФНС — статус, дата регистрации, ОКВЭД, адрес. Кэш выписок на сутки.
- Добавление своего поставщика по ИНН или ссылке на сайт — карточка заполняется сама.
- **Результат:** реальная проверка контрагента и общий шорт-лист для команды, пока без автоматического поиска.

### Этап 2. Поиск кандидатов · ~2–3 недели

- Источники: 2ГИС / Яндекс Карты (API организаций по рубрике и городу), поиск по вебу (свой SearXNG или платный поисковый API), отраслевые каталоги и маркетплейсы B2B.
- Склейка дублей: один поставщик с сайтом, карточкой на картах и юрлицом — одна запись (по ИНН, домену, телефону).
- Свой каталог поставщиков растёт с каждым поиском; повторный запрос сначала ищет в нём.
- **Результат:** по запросу находятся реальные компании с проверенным юрлицом.

### Этап 3. Сбор условий с сайтов · ~3–4 недели

- Обход сайта поставщика (Playwright для страниц на JavaScript), прайсы в PDF и Excel.
- Извлечение цен, минимального заказа, графика доставки, контактов: сначала правила и шаблоны, для сложных страниц — LLM со строгой схемой ответа.
- **Обязательная проверка цитаты:** модель возвращает значение и дословный фрагмент, код проверяет, что фрагмент есть на сохранённой странице. Не нашёлся — факт не попадает в карточку. Это то же правило, что уже работает в прототипе.
- Снимки страниц хранятся (S3-совместимое хранилище), источник всегда можно открыть.
- Приведение цен к единице (коробка 10 кг → ₽ за кг) и проверка выбросов.
- **Результат:** карточка с реальными ценами и условиями, у каждой цифры — источник.

### Этап 4. Документы и качество данных · ~2 недели

- Декларации и сертификаты — реестры ФСА; ветдокументы — ФГИС «Меркурий» (по поднадзорным объектам).
- Повторная проверка данных по расписанию: истекающие декларации, смена статуса юрлица, изменения цен.
- Набор эталонных поставщиков с проверенными вручную значениями и автоматический замер: какая доля фактов извлечена верно, сколько «не нашли», сколько ошибок. Без этого замера извлечение нельзя улучшать осознанно.
- **Результат:** данные, которым можно доверять, и цифра, которая это показывает.

### Этап 5. Работа с поставщиками · ~2–3 недели

- Отправка запроса КП с почты пользователя (Gmail / Яндекс через OAuth или общий ящик), статус «написали» ставится сам.
- Разбор ответов: присланный прайс или КП разбирается так же, как сайт, условия обновляются в карточке с пометкой «из письма от …».
- Напоминания о следующем шаге.
- **Результат:** шорт-лист превращается в рабочий инструмент закупщика.

### Этап 6. Встраивание в рабочие инструменты · по потребности

- **MCP-сервер.** Те же операции (поиск, карточка, проверка ИНН, шорт-лист) как инструменты MCP — сервисом можно пользоваться из Claude или другого ассистента: «найди трёх поставщиков лосося и сравни условия» прямо в чате. Контракт уже есть, сервер MCP — тонкая обёртка над API.
- **Telegram-бот** для быстрых запросов и уведомлений («у поставщика истекла декларация», «пришёл ответ на запрос КП»).
- **Интеграция с учётной системой** (1С, iiko, r_keeper, МойСклад — что используется): реальные объёмы закупок для поиска, текущие цены для сравнения, выгрузка выбранного поставщика.
- Публичный API и вебхуки, если сервис будет для внешних клиентов.

### Этап 7. Эксплуатация · параллельно с этапами 1–6

- Мониторинг и алерты (ошибки, недоступность источников, расход на LLM и платные API).
- Ограничения частоты обращений к сайтам и уважение robots.txt; юридическая проверка сбора данных.
- Резервные копии, журнал действий пользователей, хранение персональных данных по 152-ФЗ (серверы в РФ).
- Лимиты и оплата, если сервис коммерческий.

## Вопросы к заказчику

Ответы определяют, в каком порядке и насколько глубоко делать этапы выше.

**Пользователи и цель**
1. Кто будет пользоваться: свои закупщики Goulash.Tech, клиенты (кафе, магазины, производства) или и те и другие?
2. Сколько пользователей и поисков в день ожидается на старте и через полгода?
3. Какую задачу закупщики решают сейчас и как: Google, звонки, знакомые, агрегаторы? Что в этом больнее всего — найти, проверить или сравнить?
4. Есть ли 2–3 закупщика, с которыми можно проверить прототип и собрать обратную связь?

**Охват**
5. Какие города и категории нужны в первую очередь? Только Урал или вся Россия?
6. Есть ли уже свой список проверенных поставщиков, который стоит загрузить как стартовый каталог?
7. Какие условия решают выбор на практике: цена, минимальный заказ, отсрочка, частота доставки, документы? Совпадают ли веса оценки в прототипе с реальностью?
8. Какие документы обязательны по категориям? Нужна ли проверка через «Меркурий» для мяса, рыбы и молочки?

**Данные и источники**
9. Есть ли бюджет на платные источники (DaData, API 2ГИС, поисковый API, LLM) и какой порядок цифр допустим в месяц?
10. Допустим ли автоматический сбор данных с сайтов поставщиков? Есть ли требования юристов?
11. Насколько свежими должны быть данные: раз в день, раз в неделю, по запросу?

**Работа с поставщиками и интеграции**
12. Нужна ли отправка писем из сервиса или достаточно черновика?
13. Какая учётная система используется (1С, iiko, МойСклад и т. д.) и нужна ли с ней связь?
14. Где удобнее работать закупщикам: веб, Telegram, ассистент вроде Claude через MCP?

**Технические рамки**
15. Есть ли требования к инфраструктуре: свой сервер, облако в РФ, конкретный стек?
16. Есть ли требования по безопасности и персональным данным (152-ФЗ, хранение в РФ, доступ по ролям)?
17. Нужны ли учётные записи компаний с несколькими пользователями и правами?

**Сроки**
18. Какой срок до первой версии с реальными данными и что в неё обязательно должно войти?
19. Кто со стороны заказчика принимает решения по продукту и как часто созваниваемся?
